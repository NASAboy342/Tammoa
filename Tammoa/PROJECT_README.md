# Tammoa — backend (Photino host + minimal APIs)

.NET 8, Photino window hosting the Vue UI (`UserInterface/`), Kestrel on port 8000 for `/api/*`.

## Structure
- `Program.cs` — composition root: static file server (sealed DI) + a separate `ServiceCollection` for app services, window creation. Debug loads Vite (5173); Release loads the embedded UI with a `?v=` cache-buster.
- `Api/` — `Map<Feature>Endpoints(this WebApplication, I<Feature>Service)` per feature.
- `Services/Cards/` — one class per card type (`ICardType`), registered in `Program.cs`; `ICardRegistry` serves the catalogue. **To add a card: implement `ICardType` (+ its `CardTypeInfo` with param descriptors) and register it. No UI change is needed**, the UI draws cards and their forms from `GET /api/cards/types`.
- `Models/ Services/ Repositories/ Enum/ Helper/` — conventions in the Foundation repo (`backend-conventions.md`). `Enum/` types use namespace `Tammoa.Enums`.
- `Helper/JsonHelper` — Newtonsoft.Json (camelCase, nulls ignored, enums as strings). Never `System.Text.Json`.
- `Helper/EndpointHelpers` — `Try`/`TrySync`: `ArgumentException` → 400, `InvalidOperationException` → 409, else 500.
- `Resources/wwwroot/` — embedded built UI (keep the placeholder file, an empty folder crashes the static server).
- `AppIcon/` — the app icon (`app.ico` for the window and Windows, `app.icns` for macOS); packaging (`setup-deploy`) takes it from here.

## Storage
**SQLite** (`Microsoft.Data.Sqlite`), chosen for flows (later: run history, logs). File: `<ApplicationData>/Tammoa/tammoa.db` (macOS `~/Library/Application Support/Tammoa`); override the folder with env var `TAMMOA_DATA_DIR` (dev runs and e2e tests use a temp folder). `Repositories/FlowRepository` creates the schema in its constructor (idempotent, WAL). The flow `definition` (cards + connections) is stored as a JSON text column and never queried inside.

## Conventions
DI always, no `new` services in endpoints, JSON via `JsonHelper`. `EndpointHelpers` maps `ArgumentException` → 400, `KeyNotFoundException` → 404, `InvalidOperationException` → 409. Time comes from an injected `TimeProvider`.

## Cards, runs and the engine (everything executes in the backend)
- **Definition** (stored in the flow row, validated by `FlowDefinitionValidator` on every save and import): `{ schemaVersion, nodes: [{ id, type, name, position:{x,y}, params }], edges: [{ id, source, target }] }`. Rules: known card types, unique ids, edges point at existing cards, no self/duplicate links, triggers have no input, max 200 cards; optional `groups` (see below). **Cycles are allowed (that is a loop)**; optional `settings.loopLimit` (whole number 1..1000) and per-card `size { w, h }` (numbers 40..1600) are validated too.
- **Data flow:** a card's `input` is its parent's output (an array of outputs when it has several parents; null for a trigger). Templates in params: `{{input.path[0].x}}`, `{{run.input}}`; a string that is exactly one `{{ }}` keeps its JSON type; filters `| json`, `| sh` (POSIX quoting; `TODO` Windows). Missing paths give empty text / null. Template values are inserted as-is: use `| sh` whenever a value goes into a shell command.
- **Engine** (`FlowExecutor`): cards whose parents all succeeded run concurrently; a failed card makes everything downstream `skipped` and stops scheduling new cards; cancel marks unfinished cards `cancelled`; cards not reachable from a trigger are `skipped`. Config errors (`ArgumentException`) and work errors (`InvalidOperationException`) become the card's `error`.
- **Runs** (`RunService`): `POST /api/flows/{id}/runs` returns `202` + the first snapshot at once and runs in the background; any number of runs execute at the same time. The run uses the definition as it was when started. **Snapshots are immutable and carry a `revision`** that grows with every change: clients keep the highest revision (a pushed event and a fetched reply can arrive in either order).
- **Live state:** `GET /api/events` is a server-sent-events stream of complete run snapshots (`event: run`), 15 s keep-alive comments, per-subscriber buffer that drops the oldest. The UI holds no run logic; it displays what arrives.
- **Branching:** a card can have several named outputs (`CardTypeInfo.Outputs`, default one `main`; IF has `true` and `false`). An edge is `{ id, source, sourceHandle?, target }` (handle defaults to `main`, validated against the source card's outputs). A card returns `CardResult(output, branch?)`; with a branch only that handle's connections are active. A card waits for all its parents to finish, then runs if **at least one** incoming connection is active (input = that output, or an array of the active outputs); with none active it is `skipped`, and the skip cascades. A skipped branch is not a failure.
- **Cards** (all in `Services/Cards/`, registered in `Program.cs`; the UI needs no change for a new one):

  | Type | Category | What it does / output |
  |---|---|---|
  | `trigger.manual` | trigger | starts the run; `{ input }` = the value passed with the run |
  | `logic.if` | logic | outputs `true` / `false`; operators equals, notEquals, contains, notContains, startsWith, endsWith, greaterThan, lessThan (numbers), isEmpty, isNotEmpty, matches (regex, 1 s limit); passes its input through |
  | `flow.wait` | logic | waits 0-3600 s (cancellable), passes input through |
  | `data.set` | data | JSON object built with templates (JSON editor) |
  | `data.json` | data | parse text → data (non-objects become `{ value }`) or stringify data → `{ text }` |
  | `data.merge` | data | merges the objects of several incoming connections (later wins) |
  | `script.shell` | action | **Shell, JavaScript (Node) or Python** (see below); output `{ stdout, stderr, exitCode, timedOut, truncated, json? }` |
  | `net.http` | action | HTTP request (GET/POST/PUT/PATCH/DELETE/HEAD, http(s) only, headers JSON, body, timeout, fail on non-2xx); output `{ status, ok, headers, text, truncated, json? }`; response capped at 1 MB |
  | `file.read` / `file.write` | action | UTF-8 text files; absolute paths or `~/`; read limit in KB; write overwrites or appends, can create folders. **Read output is `{ path, text, size, exists, input }`; `input` is a copy of what the card received (null for none), so the next card still has it (`{{input.input.x}}`). A missing file is not an error:** `text` is empty, `size` 0, `exists` false; the `createIfMissing` switch (default off) creates the empty file and its folders first; an existing file is never touched; a path that is a folder fails |
  | `ai.ollama` | ai | one chat turn with an Ollama model (see Connections), **streamed and shown live**; output `{ text, thinking?, model, done, doneReason, promptTokens, responseTokens, totalDurationMs, json? }` |
  | `data.store` | data | **reusable text** in a `.txt` file, readable from any card as `{{data.Name}}` (see Data cards); a source: runs with no trigger and no connection; output `{ text, json?, name, scope, size, updatedAt, changed }` |

- **Script languages:** `language` = shell (default; templated with `{{ }}`) | javascript | python (not templated). JS/Python code is written to `script.js` / `script.py` and started through a tiny **wrapper** (`wrapper.js` / `wrapper.py`) that defines the ready-made variables and then loads the user's file untouched, so **error line numbers are those of the user's code** (`script.js:3`). Run with `node` / `python3` (`python` on Windows) or the card's `interpreter`.
  - **Reading the input:** JavaScript `input` and `runInput` (globals; CommonJS, so `require()` works and a top-level `return` is fine, `import` does not) · Python `input_data` and `run_input` (**not** `input`, which would hide Python's `input()`) · shell `{{input.x | sh}}` templates. In every language: env `TAMMOA_INPUT` / `TAMMOA_RUN_INPUT` (JSON text, set when ≤ 64 KB) and `TAMMOA_INPUT_FILE` / `TAMMOA_RUN_INPUT_FILE` (temp files, always set; the wrappers read these), plus `TAMMOA_SCRIPT_FILE`.
  - **Handing data on:** if stdout is JSON it is `output.json`; if not, the **last line** is tried, so a script can log progress and finish with its JSON. Exit code 127/9009 gives "'node' was not found. Install it or set the Interpreter setting." Temp files are deleted after the run. Flows saved before languages existed have no `language` and run as shell.
- **Param kinds** (`ParamKind`): text, textarea, number, bool, **select** (fixed `options`, or `optionsSource` + `optionsDependsOn` loaded from `GET /api/cards/options/{source}?connectionId=`), **code** (`codeLanguage` or `codeLanguageParam`), **connection** (`provider`).

## Data cards (reusable text, no trigger needed)
- **What it is:** `data.store` keeps a piece of text in a plain `.txt` file: typed by hand (the `value` param has kind `Stored`: it is edited and saved on its own through `PUT /api/flows/{id}/data/{cardId}`, **not** in the flow definition) or written by a flow (connect a card INTO it, choose `mode` replace | append and `writeFrom`, a template, default `{{input}}`; default mode is **keep**, so a connection never overwrites by accident).
- **Reading it: by NAME, from any card of the flow, no wiring, no trigger.** `{{data.Style}}` in any template; if the text is a JSON object or list it is parsed (`{{data.Settings.city}}`), anything else (even `42`) stays text. Scripts get `data` (JavaScript, Python) and `$TAMMOA_DATA` / `$TAMMOA_DATA_FILE`. The card's **name** is the reference name: validated on every save and import (`DataNames`: not empty, ≤ 60, none of `. [ ] | { }`, unique in the flow case-insensitively; `scope` must be `flow` or `shared`).
- **Sources:** `CardTypeInfo.IsSource` marks a card that runs at the start of a run with nothing connected and no trigger. A flow still needs a trigger to start. Every card gets `context.Data` = all Data cards of the flow, **re-read when that card starts**, so a Data card updated earlier in the run is seen by the cards after it.
- **Storage:** `DataRepository`, files under `<data folder>/data/`: `flows/<flowId>/<cardId>.txt` (scope `flow`, default) or `shared/<name>.txt` (scope `shared`: every flow with a Data card of that name shares it; lower-cased and sanitised). Atomic writes (temp file then move), mode 600, limit 1 MB. Ids and names can never climb out of the folder.
- **Lifecycle:** deleting a flow deletes `flows/<id>/`; duplicating copies it; `FlowDocument.Data` (cardId → text, flow-scoped cards only, omitted when empty) carries it through export/import (shared texts stay on the computer).
- **API:** `GET /api/flows/{id}/data` (cards with preview), `GET`/`PUT /api/flows/{id}/data/{cardId}` (`{ text }`; 400 over 1 MB, 404 for an unknown flow or a card that is not a Data card of the saved flow). Every write publishes `event: data-changed` `{ flowId, cardId }` on `GET /api/events`.

## Live output of running cards
- A card can report what it has produced so far: `CardExecutionContext.Progress(JToken)`. The engine puts it in `NodeRun.Live` (cleared when the card finishes, replaced by `Output`) and publishes a snapshot, **at most one per card per 150 ms** (`FlowExecutor.LiveInterval`): the first value at once, the rest coalesced, the last value always flushed shortly after. Late reports from finished or cancelled cards are ignored.
- **Thread safety:** cards report from their own threads, so everything that changes `run`/`status` happens under one lock and `onChange` is called inside it: snapshots reach the repository and the clients in revision order (tested with many threads reporting while the run finishes).
- **Ollama streaming:** `OllamaClient.ChatAsync` streams (`"stream": true`, newline-delimited JSON) and calls `onDelta(thinkingSoFar, textSoFar)` per piece; the card turns that into `Live = { text, thinking? }`. The card's timeout is now **silence**: it restarts with every piece, so a long answer that keeps coming is never cut off, and a model that goes quiet fails with "was silent for N s". Cancelling the run closes the stream.

## Tutorials and "what is my input" (data the UI shows)
- **`NodeRun.Input`:** every card's run record keeps the input it received (absent for triggers, which take the run input, and for skipped cards; kept for failed cards). The UI shows it in the Input tab.
- **`CardTypeInfo.Guide`** (`CardGuide`): `Overview`, `InputNote` (how this card's input arrives), `OutputExample` (also the "fields this card will provide" shown to the card connected after it, before anything ran), `Examples` and `Tips`. A `GuideExample` has `Title`, `Description`, `Params` (what "Use this example" applies; every key must be a real setting and every Select value a real option), `Code`, `Language`, `SampleInput`, `RunInput` and `Result`. Code params can also carry `CodeHelp` (one-line hint per language under the editor) and `CodePlaceholders` (starter per language).
- **The guides are tested, not trusted** (`CardGuidesTest`): every card has a complete guide; example settings are valid; **every local example is executed** against its sample input and its claim is asserted (adding an example without an expectation fails the suite, which is how a wrongly-placed sample input was found); the documented output fields exist in the real output. When you add a card or an example, write its guide and its expectation.

## Connections (addresses and keys of AI services)
- `Models/Connection` (internal, has the key) vs `ConnectionInfo` (what the API returns: `hasKey` only). `ConnectionProvider` currently has `Ollama`; add OpenAI/Anthropic there plus a client and card each.
- Endpoints: `GET /api/connections/providers`, `GET/POST /api/connections`, `GET/PUT/DELETE /api/connections/{id}`, `POST /api/connections/{id}/test` (always 200: `{ ok, version, models, error }`). Update: `apiKey` empty keeps the saved key, a value replaces it, `clearApiKey` removes it. Delete returns 409 naming the flows whose cards still use the connection.
- **Where the key lives:** plain text in the `connection` table of `tammoa.db`. `DataPaths.RestrictToOwner` makes the data folder owner-only (mode 700) at startup (macOS/Linux; **Windows not handled**). The key is never returned, logged or put in exports (cards hold only the connection id). Moving to the OS keychain is a possible later change behind `IConnectionRepository`.
- `OllamaClient` (`/api/version`, `/api/tags`, `/api/chat` non-streaming): sends `Authorization: Bearer <key>` when a key is set (for servers behind an auth proxy); readable errors for unreachable servers, 401/403, unknown model, non-Ollama answers, timeouts. Ollama card `think`: auto sends nothing, on/off sends `think: true/false`.

## Run log
`DELETE /api/runs/{id}` (409 while running), `DELETE /api/flows/{id}/runs` (deletes finished runs, returns `{ deleted: [ids] }`, running ones stay). Every removal is pushed as `event: run-removed` (`{ runId, flowId }`) on `GET /api/events`. After a run ends, a flow keeps only its newest 50 finished runs (`RunService.MaxRunsPerFlow`); the repository also caps the total at 200.
- **Context size:** the ai.ollama param `numCtx` is the `num_ctx` option; Ollama's own default is small (often 2048-4096) and silently drops the START of a long prompt, so long tasks and tool use should set it (16384 is a good start; more memory and slower).
- **Stubs / not built:** run history is in memory only (`RunRepository`, lost on restart; `TODO(persist runs)`); `enabled` flows do nothing yet (no scheduler/triggers); model cards with tool use (design discussed, not built).
- **Security note:** the script card runs arbitrary commands as the current user. It is a local desktop app and the user writes the flows, but never run an imported flow you have not read.

## Loops (a connection back to an earlier card)
- **Detection** (`LoopAnalysis`): a depth-first walk from the cards with nothing connected into them marks the edges that return to a card on the current path as **back edges**; strongly connected groups of more than one card are the **loops**. The forward part of the graph is scheduled exactly as before.
- **Running a loop** (`FlowExecutor`): when a card finishes and a back edge from it is active (right branch handle), the target is queued. When no member of that loop is still running, the loop's cards are archived into `NodeRun.Previous` (last 10 rounds, `NodeIteration`), reset to pending, and the target starts again with the source's output as input (an array when several back edges fired). Cards **after** the loop wait until it has no pending or running member, so they run once, on the last round, and are never skipped early. **Side branches:** a card hanging off a *non-branching* loop card (e.g. Write file after a JSON card inside the loop) is not the exit; it follows the loop's rounds (runs every round, reset with the loop). Only cards reached through a branching card's output that leaves the loop (IF *false*) wait for the end.
- **Loop limit:** each card may start at most `settings.loopLimit` times per run (default 50). The card that would start once more fails (`Loop limit reached: '<card>' already ran N times...`), which fails the run. `NodeRun.Iteration` is the number of rounds the card really made.
- Not allowed: a card connected to itself, a connection into a trigger. Cancel works in the middle of a loop.

## Groups (canvas organisation only)
- `definition.groups` = `[{ id, name, nodeIds }]`; the engine ignores it. `FlowDefinitionValidator` checks: array; id 1..64 chars and unique; name 1..60 characters (trimmed); `nodeIds` an array of existing card ids; a card in at most one group (also not twice in one). Groups travel through duplicate and export / import with the rest of the definition (validated again on import).

## Flow files (export / import)
A flow is portable: `GET /api/flows/{id}/export` returns a `FlowDocument` `{format: "tammoa.flow", version: 1, name, description, definition}` — no id, enabled state or timestamps. `POST /api/flows/import` creates a new, disabled flow from one (400 on wrong format or a newer `version`). `definition.schemaVersion` versions the card JSON itself for future migrations. **Never put secrets (API keys) in a definition**: cards must reference credentials by name, so exported files are safe to share.

## AI agent control (an assistant builds flows through the API)
- **Rule for every contributor: when you add or change an API route, update the agent skill.** `Services/AgentApi.cs` lists every route (`Routes` = an agent may call it, `NotForAgents` = it may not, with the reason); a test (`AgentAccessTest.EveryRouteOfTheApp_…`) fails when a route is in neither list. A route an agent may use also needs a line in `AgentSkill/tammoa-flows/SKILL.md` if it changes how a flow is built. The routes table and the card catalog of the served skill are generated from the code, so new cards and parameters appear by themselves; the hand-written `SKILL.md` covers the concepts (definition format, `{{ }}` references, safety rules) and must stay true when those change.
- **How it works:** the user switches **Agent access** on in the UI (off by default, `agent-access.json` in the data folder: `enabled`, `allowRun`, `token`). A request with `Authorization: Bearer <token>` is an agent: `AgentAccessMiddleware` (`Services/AgentAccessService.Check`) refuses a wrong token (401), access that is off, or a route outside `AgentApi.Routes` (403); starting a run also needs `allowRun`. A request without the header is the app's own UI and is never restricted (so the token scopes an agent, it does not lock the local API). The agent cannot delete flows/runs, touch connections or read/change the token and switches.
- **Routes:** `GET/PUT /api/agent/access`, `POST /api/agent/access/token` (the UI), `GET /api/agent/skill` (Markdown: `AgentSkill/tammoa-flows/SKILL.md` embedded in the app + the address + the routes + the card catalog; UI copies it without a token, an agent reads it with one), `POST /api/flows/validate` (dry check, nothing saved: `{ valid, error? }`).
- The address in the UI is the API's own address (`apiUrl` in `Program.cs`: the Vite UI is on another port in dev; in a packaged app the UI and the API share the server).

## First run, templates, settings, backup, updates
- **Flow templates** (`Services/FlowTemplateService`, `GET /api/templates`, `POST /api/templates/{id}/create`): five ready flows kept as JSON in code (Hello (script, no AI), Choose a path (IF), Call a web API, Summarize text, Summarize a file; the last two need Ollama). `Create` goes through `IFlowService.Import`, so a template is a normal, validated, **disabled** flow; for a template with an AI card the chosen connection (and model) are written into every `ai.ollama` card, otherwise the card asks. **Tested, not trusted** (`FlowTemplateServiceTest`): every template validates, uses only real card settings (checked against the real cards), has one trigger and no overlapping cards, and the no-AI ones are executed for real. When you add a template, add its id there.
- **Settings** (`ISettingsService`, `settings.json` in the data folder, `GET/PUT /api/settings`): one switch for now, `checkUpdatesAtStart` (off by default).
- **Update check** (`UpdateService`, `GET /api/app/update`): asks `https://api.github.com/repos/<owner>/<repo>/releases/latest` (the repository comes from `<AssemblyMetadata Include="RepositoryUrl" …>` in `Tammoa.csproj`: change it there if the repository moves) and compares numbers (0.10 is newer than 0.9; a pre-release suffix is ignored). **Never throws**: offline, no release yet (404), rate limit and unreadable answers come back as `{ error }` in plain words. Only a `github.com` address is returned as the link. Sends no personal data (User-Agent `Tammoa-update-check`). The app asks only when the user presses the button or switched the start check on.
- **Backup** (`BackupService`, `/api/backup*`): one JSON file `tammoa-backup-<UTC time>.json` in `<data folder>/backups/`: flows (with the text of their own Data cards), connections **without keys** (`hasKey` says whether one existed), shared Data texts. **Not in it:** keys, run history, the agent token. Restore **never overwrites**: flows and connections keep their ids, so restoring the same file twice adds nothing and cards that name a connection work again; flows come back disabled; a flow that fails validation is listed in `problems` by name and does not stop the others; ids from the file are checked (`BackupIds`) before they reach paths or the database. `POST /api/backup/restore` takes the document (the UI sends a chosen file), `restore-file` takes a name in the backups folder (letters, digits, `.-_`, `.json` only), `open-folder` shows the folder in Finder/Explorer (`FolderOpener`, the path is an argument, never a command line). A file is written to the folder instead of "downloaded" on purpose: a download from the WebKit window is not reliable.
- All of these routes are in `AgentApi.NotForAgents` (they belong to the user).
